# Engineering rules

These constraints apply to contributions throughout this repository. See [architecture](docs/public/architecture.md) and [validation status](docs/public/validation-status.md) before changing behavior.

1. **Portable ECS authority.** Gameplay belongs in plain C# entities, data components and explicitly ordered systems. Keep stable IDs and generation-safe runtime handles. Components do not contain engine objects or hidden gameplay methods. Godot Nodes and future Unity MonoBehaviours are adapters, not a second authoritative simulation.
2. **Unity portability.** Preserve the engine-neutral core and its declared target/language compatibility. Godot/Unity types, engine clocks, filesystem I/O and global randomness must not leak into Core. ECS does not imply Unity DOTS, Jobs or Burst; new frameworks require an explicit dependency/portability decision.
3. **Deterministic boundaries.** Use fixed ticks, explicit commands, seeded RNG and stable execution ordering. Define pause, catch-up, cancellation and event-overflow behavior. Same-build seeded regressions do not imply cross-platform floating-point bit identity.
4. **Composable content.** Separate stable skill/character/item definitions from runtime state. Extend narrow data contracts and systems rather than central name-based branches or cross-skill private-state access. Validate references, ranges and schema versions. Avoid speculative generic frameworks.
5. **Presentation ownership.** UI sends intent; rendering, animation, audio and input display snapshots/events. Cosmetic budgets cannot drop business effects or write damage. Declare event phases and units. Track full identities through pooling, reset and disposal; never dispose shared resources as if privately owned.
6. **Save safety.** Treat migrations as explicit durable transactions. Preserve original data and backups, validate authority selection, and fail closed on uncertainty. Do not silently resurrect Closed/PendingStart runs or infer consent from a previous process.
7. **Traceability.** Record each change's requirement, scope, design decision, alternatives, compatibility impact, test result and known limitations in concise public-safe documentation and commits. Keep failed/superseded results identifiable; do not erase counterevidence or claim unrun tests passed. Full private operational logs need not be published.
8. **Validation.** Run affected Core and adapter tests, lifecycle/reset/error cases and applicable native UI/visual checks. Headless success cannot establish appearance, device support, performance or export correctness. Preserve old tests unless a deliberate authorized rule change explains their update.
9. **Collaboration.** Work on isolated branches/worktrees with a known baseline, small commits and explicit ownership. Do not overwrite others' work, force-push shared history, merge or deploy without authorization. Draft PRs are preferred when a PR is requested.
10. **Publication.** The owner has chosen public source publication. Publish only authorized code, necessary assets, provenance/licenses and concise design/test status. Never include credentials, user saves, internal identifiers, private paths, unrequested recordings or recovery transcripts. Do not silently change repository visibility. Keep caches, build outputs and signing keys out of Git.

Decoupling, ECS gameplay authority, Unity portability and auditable decisions remain required even when a prototype is intentionally marked WIP.
